# AGENTS.md

## Project Context

This is a fork of a Base44 app with everything except the AI assistant's *brain* moved off Base44. Core app data (areas, products, projects, tasks, stakeholders, departments, notes) lives locally via `src/lib/localDb.js` by default — no hosted database, and as of the chat rewrite below, the AI assistant reads and writes this exact same data too. `localDb.js` picks its backing store automatically per session: real JSON files in a gitignored `data/` folder when running `npm run dev`/`npm run preview` (served by `vite-localdb-plugin.js`'s dev-server middleware), or, everywhere else (hosted preview, production build, standalone distributables — anything with no Node process behind it), `src/lib/deviceStorage.js` — see its own Key Files entry below. **This is not `localStorage`** — that was the behavior before 2026-07-23; `localStorage` is now only read once, as a legacy carry-forward for returning users, never written to again. Base44 is retained to run the LLM call itself (`base44/functions/aiChatStream`), store chat history (`ChatSession`/`ChatMessage`), gate access to the app (login), and, only if a user opts into cloud storage, hold their project data too (`src/lib/cloudStorage.js`).

Important: `aiChatStream` never touches your project data. It used to execute actions directly against Base44's own hosted entities — a separate, disconnected dataset from what the Dashboard showed, which meant chat could never visibly affect anything you saw. That's been rewired: the client now sends its current local dataset along with each message (so the LLM can see it), the function decides a plan and returns it *unexecuted*, and `src/lib/chatActions.js` runs it client-side against `localDb` — the same cascade logic the UI's own mutation hooks use (imported directly, not duplicated). Your data touches Base44 only in transit, for that one request; nothing is persisted there. A privacy notice (the `Info` icon) in both chat surfaces says exactly this.

Treat this as user-owned application code, keep changes focused on the user's request, and preserve existing project conventions.

Start with `README.md` for local setup and architecture details.

## Key Files

- `src/lib/localDb.js`: the local data layer for all app data, now including what the chat assistant reads/writes. Two backing stores (file-backed via the dev-server API, or `deviceStorage.js`), chosen automatically by a probe on first read — every exported function stays `async` regardless of which is active, so nothing calling it needed to change.
- `vite-localdb-plugin.js`: the Vite dev/preview-server middleware backing the file-based store above — reads/writes `data/<collection>.json`. Only active under `npm run dev`/`npm run preview`; has no effect on a production build or any other deployment target.
- **Device/cloud storage** (as of 2026-07-23, cloud added 2026-07-26 — replaced browser `localStorage` entirely, see `README.md`'s "Local data storage" for the user-facing version of this): `src/lib/deviceStorage.js` is what `localDb.js` reads/writes through whenever the dev file-backed store isn't available. Three backends, picked by explicit user choice (`getStorageMode`/`setStorageMode`, `vaea_storage_mode` — the one deliberate exception to "no app data in browser storage," since it's not data, it's which storage holds the data): File System Access (`supportsFileSystemAccess`; a granted folder, one `<key>.json` file per collection, handle persisted in its own IndexedDB store so a return visit only needs a one-click permission re-grant); manual mode (every other browser — an in-memory store, loaded/saved via `loadSnapshotFile`/`downloadSnapshotFile`); and cloud (`src/lib/cloudStorage.js`, dispatched to when `getStorageMode() === "cloud"` — a Base44-hosted `AppData` entity, one row per key, RLS-scoped to the signed-in user, requires a real session). `src/components/shared/DeviceStorageGate.jsx` (wraps the authenticated app in `App.jsx`) blocks all rendering until a backend is ready: first run asks cloud-vs-device (skipped, defaulting silently to "device," for anyone who already had FSA/manual storage connected before this choice existed), then handles FSA permission re-grants, manual file load, and cloud sign-in-required prompts. It also carries forward any pre-existing browser-storage data (entities, AI identity, vault connection) via `localDb.js`'s `readLegacyLocalStorageData`/`seedCollections` and friends. `src/components/settings/StorageSection.jsx` is the Settings → Data Storage UI for switching device ⇄ cloud later, using `src/lib/storageMigration.js`'s `copyAllKeys` to carry data across in either direction rather than starting empty.
- `src/hooks/`: entity hooks (`useAreas`, `useProducts`, `useProjects`, `useTasks`, `useStakeholders`, `useDepartments`, `useProjectNotes`) — each exports both a React Query mutation hook (for the UI) and the plain async function it wraps (for `chatActions.js` to reuse directly). Keep it that way — don't let the chat executor drift into its own copy of cascade logic.
- `src/lib/chatActions.js`: the chat assistant's action executor — mirrors `aiChatStream`'s action catalog 1:1, but runs against `localDb` via the hook files' plain functions above. This is what actually creates/updates/deletes things when you chat.
- `src/hooks/useChatController.js`: gathers the local dataset snapshot sent to `aiChatStream`, and calls `chatActions.js` to execute (or hold for confirm, or undo) whatever plan comes back.
- `src/api/base44Client.js`: frontend Base44 SDK client, used only for chat (`useChatController`, `useChatSessions`, `useChatMessages`) and its file attachments.
- `base44/functions/aiChatStream/`: decides the action plan only, never executes it. Requires an authenticated session (rejects with 401 otherwise) since it's reachable by URL and would otherwise let anyone burn LLM calls.
- `base44/functions/deactivateAccount/`: restored account-deletion function, callable only by the authenticated user on their own account.
- `src/lib/AuthContext.jsx` + the `AuthenticatedApp` wrapper in `src/App.jsx`: gates the whole app behind base44's own hosted login (Google/Microsoft/Apple/email) by default — same pattern as Zmanim Today. Restored from pre-fork history at the user's explicit request; don't remove without being asked, same as you wouldn't have added it without being asked. As of 2026-07-24, `LoginScreen.jsx`'s "Continue without signing in" link is a deliberate, explicitly-requested opt-out of that gate (`continueAsGuest()`, remembered via the `vaea_guest_mode` localStorage flag `AuthContext.jsx` checks in `checkAppState()`) — a guest reaches the dashboard (already fully local-data-only) but chat still enforces real auth on its own via Base44 RLS + the existing 401/403 → `ChatAuthPrompt` handling. Don't remove this opt-out without being asked either — it's had one prior round of being added, then removed for contradicting the whole-app-gate directive, then re-added at the user's explicit request; check with the user before changing course again.
- `src/lib/CardViewContext.jsx`: the "mini" vs "full" project-card preference, toggled at the top of the Dashboard and shared by `AreaCard`/`ProductCard` (which switch both which `ProjectCard*` component renders and their container's layout class). `ProjectCard.jsx` (mini, default) and `ProjectCardFull.jsx` (the original always-editable card, restored from pre-mini-cards history) are both real, maintained components — don't treat one as dead code.
- `vite.config.js`: Vite config and Base44 Vite plugin setup — kept because `aiChatStream` still needs the Base44 toolchain.
- `src/lib/csv.js`: generic, entity-agnostic CSV parse/stringify (no external dependency — hand-rolled but RFC4180-correct: quoted fields, embedded commas/newlines, escaped `""` quotes).
- `src/lib/csvImport.js`: ONE CSV template covering the whole area -> product -> project -> task hierarchy in a single file (not one template per entity type) — a row spells out the full parent path down to whatever it's adding, leaving deeper columns blank once it's reached that level. Repeating the same title across rows (or matching an already-existing record) reuses that record instead of duplicating it. Builds an ordered `CREATE_AREA`/`CREATE_PRODUCT`/`CREATE_PROJECT`/`CREATE_TASK` action plan with `$temp_id` chaining — the *exact* mechanism `aiChatStream`'s own multi-step plans use (see `[MULTI-STEP PLANS]` in that function and `chatActions.js`'s `resolvePlaceholders`) — and runs it through `executeActionSequence`. Don't add a second id-resolution or plan-building implementation; this reuses the one that already exists for chat.
- `src/components/modals/CsvImportForm.jsx`: the "Via .csv" tab's UI — download the template, upload a filled-in file, shows per-entity-type creation counts plus any per-row errors (a bad row doesn't block the rest of the file).
- `src/lib/backupSnapshots.js`: a same-day rollback safety net for local data — `chatActions.js`'s `executeActionSequence` snapshots every collection to `deviceStorage` (never `localStorage` — see the device/cloud storage entry above) before running any multi-step plan or bulk create/delete (this is also what protects CSV import, since it runs through the same function). `src/components/settings/BackupRestoreSection.jsx` lists and restores snapshots from Settings; restoring itself takes a fresh "before restore" snapshot first, so it's never a one-way door. Capped at the 8 most recent. Deliberately separate from `UNDO_LAST_ACTION` (`useChatController.js`), which only pops one action from in-memory state and doesn't survive a reload.
- `src/pages/VaultSetupGuidePage.jsx` (route `/settings/vault-setup`, linked from `src/components/settings/ResourcesSection.jsx`): a real page, not a chat command — a walkthrough for setting up an external, git-backed Obsidian notes vault from scratch. Terminal commands render via `src/components/settings/TerminalBlock.jsx`, a dark terminal-chrome block (JetBrains Mono, loaded in `index.css` as `--font-terminal`/`font-terminal` but otherwise unused) whose `$` prompt color follows the user's chosen accent from `useAccentTheme.js`. Copy-to-clipboard follows the same icon-swap-to-checkmark pattern as `AiPreferencesSection.jsx`'s Save and `BackupRestoreSection.jsx`'s Restore, not a toast.
- **Vaea Vault connection** (the assistant actually reading/writing that repo, not just a guide to set one up by hand — user-facing name as of 2026-07-24, was "External Vault"; `ExternalVaultSection.jsx`/`vaultConnection.js`/`externalVault` etc. keep their original internal names, this is a copy-only rebrand): `src/lib/vaultConnection.js` stores the connection (owner/repo/branch/token) via `deviceStorage` (never `localStorage`), same pattern as `aiPreferences.js`. `src/lib/githubApi.js` holds the client-side GitHub REST calls (`testVaultConnection`, used by `src/components/settings/ExternalVaultSection.jsx`'s Connect button; `writeVaultFile`, used by `chatActions.js`'s `WRITE_VAULT_NOTE` case) — UTF-8-safe base64 helpers here matter, since plain `btoa`/`atob` mangle anything outside Latin1 and note content is real user text. `useChatController.js`'s `invokeAssistant` sends the connection (including the token) with every request, transiently, the same way it already sends `aiIdentity` and the local dataset — `base44/functions/aiChatStream/entry.ts` never persists it, only reads it within that one request's tool calls. Read tools (`list_vault_notes`, `read_vault_note`, `search_vault`, `audit_vault`) are LIVE — real `fetch` calls to the GitHub REST API from inside the Deno function, same category as `web_search`/`search_workspace`, so their results feed back into the model's next reasoning step (this is what makes `/vault-tidy` actually work: read many notes, find broken links, propose fixes, not just one blind pass). `WRITE_VAULT_NOTE` is STAGED like every CRUD tool — queued, then executed client-side via `githubApi.js`'s `writeVaultFile`, which looks up the current file's sha itself so an update never needs the model to have tracked it correctly. Deliberately not in `DESTRUCTIVE_ACTIONS`: git's own history is treated as the undo mechanism here, not `backupSnapshots.js` (which only covers `localDb` collections and has nothing to do with an external repo).

- **Bring-your-own-key chat** (as of 2026-07-24): `src/lib/aiProviderConfig.js` stores the user's chosen provider/model/API key (Settings -> AI Model, `src/components/settings/AiModelSection.jsx`) via `deviceStorage`, same local-only pattern as `vaultConnection.js`. `src/lib/llm/` is a full second "brain," parallel to `aiChatStream`, that runs entirely client-side when BYOK is configured: `providers.js` (the catalog — Anthropic, OpenAI, Google via Gemini's own OpenAI-compatibility endpoint, xAI, each just a base URL/model list away from one of two adapters), `toolCatalog.js` (a hand-kept JSON-Schema port of `entry.ts`'s Zod tool defs — keep both in sync when the action catalog changes), `systemPrompt.js` (ditto for `buildInstructions`/`buildContextPrompt`), `localTools.js` (client-side `search_workspace`/`audit_workspace`, the only two "live" tools portable without a backend), `toolRunner.js` (the shared stage-vs-run-for-real dispatch both adapters call), `anthropicAdapter.js`/`openaiCompatibleAdapter.js` (the actual multi-round tool loops, direct browser -> provider, no server in between), and `byokChat.js` (the orchestrator `useChatController.js`'s `invokeAssistant` calls instead of `base44.functions.invoke` when `isByokConfigured()`). Same `{reply, actions}` contract either way, so `chatActions.js`, confirm/undo, and tool-log rendering never need to know which path answered. As of commit `23a86e5` (2026-07-28, "Full BYOK/Backdoor Mode feature parity"), Vaea Vault tools (`WRITE_VAULT_NOTE` and the read tools) and attachment reading work in BYOK mode too — `localTools.js`/`githubApi.js` give it its own client-side GitHub layer and a plain-`fetch`-based attachment reader (images ride as a real multimodal content block; plain-text files are read directly; PDFs/Office docs return an honest per-call error, no parser for those exists here). The one real, still-provider-dependent gap is web search: Anthropic and xAI have their own native hosted search wired directly into their adapters (transparent to the model — Claude/Grok already know how to use it, nothing here has to tell them), but OpenAI/Google BYOK have none at all — the system prompt tells the model this outright rather than letting it guess. `src/lib/llm/*.test.js` covers the tool-call loops against a mocked `fetch` — no real API key needed to test the wiring itself.

- **Backdoor Mode** (as of 2026-07-24): a third `src/lib/llm/providers.js` entry (`id: "local-bridge"`, `adapter: "local-bridge"`) alongside the BYOK ones above, for an enterprise's own local/on-prem model — no API key, no HTTP call at all. `src/lib/llm/localBridgeStorage.js` is a File System Access folder connection (same shape as `deviceStorage.js` — a folder the user grants access to once, the handle persisted in its own IndexedDB store — but a completely separate handle, since this is a request/response transport, not app data) that auto-creates `prompts/` and `responses/` subfolders in it. `src/lib/llm/localBridgeAdapter.js`'s `callLocalBridge` runs the same plan-then-tools round loop shape as `anthropicAdapter.js`, except each round writes `prompts/<requestId>-r<round>.json` (`{round, system, tools, messages}`, Anthropic content-block shaped) and polls `responses/<requestId>-r<round>.json` every 5s until the user's own local watcher script — running wherever their model actually lives, watching the same folder — answers it with `{content: [...]}`. `byokChat.js`'s `runByokChat` dispatches to this adapter too (despite the function's BYOK name — it decides the plan client-side the same way, so it shares the dispatch rather than a parallel copy) when `provider.adapter === "local-bridge"`, checking `localBridgeStorage.js`'s live connection status instead of an API key. `useChatController.js` routes here via `isLocalBridgeConfigured()` (`aiProviderConfig.js`) alongside the existing `isByokConfigured()` check. `AiModelSection.jsx`'s `BackdoorModeConnect` is the folder-connect UI (mirrors `ExternalVaultSection.jsx`'s connect/disconnect pattern) for this provider instead of the key/model fields BYOK gets, linking to `src/pages/BackdoorModeSetupGuidePage.jsx` (route `/settings/backdoor-setup`) — the file-protocol spec and example watcher scripts (Chromium desktop only, same `supportsFileSystemAccess` gate as `deviceStorage.js`). Same limits as BYOK (see above): web search isn't available (Backdoor Mode isn't Anthropic or xAI, so there's no native hosted search to inherit), but Vaea Vault tools and attachment reading work the same as everywhere else.

## Working Notes

- Most feature work needs nothing but `npm run dev` against local data. Note: `npm run dev` locally has no real base44 app id wired, so the auth check in `AuthContext.jsx` fails with a 404 (not the real backend's 403) and silently falls through to rendering the app — this is a pre-existing quirk in the auth-check code, not a bug introduced by restoring it. The actual auth gate only meaningfully exists on a properly configured/deployed base44 app.
- Only touch `base44 dev` / the Base44 CLI when working on the AI chat function itself.
- Non-chat file uploads (`useFileUpload`, and the stakeholder avatar uploads in `StakeholderList.jsx`/`AddStakeholderModal.jsx`) store files as data URLs locally — don't reach for `base44.integrations.Core.UploadFile` there. The chat widget's own attachment upload in `useChatController.js` is the one exception, left on Base44 intentionally.
- Login is required for the whole app by default (restored from the pre-fork state) — don't remove it without being asked, mirroring the original instruction not to add it without being asked. A user can explicitly opt out via LoginScreen's "Continue without signing in" (see `AuthContext.jsx`'s `continueAsGuest`); this doesn't weaken the gate itself, it's a remembered per-visitor choice, and chat still requires real auth regardless of it.
- Run the relevant checks from `package.json` before finishing code changes.
